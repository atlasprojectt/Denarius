## 1. Principles

- One question drives everything: **"am I in control of AI spend?"** answered in â‰¤10s.
- **Verdict-first**: the screen states the conclusion (one deterministic sentence + color); details justify it below.
- Money headlines; tokens are drill-down. Semaphore colors (green/amber/red) are **reserved for budget status** â€” deltas and everything else stay neutral.
- Honesty in the chrome: "as of <date>" stamps, stale banners, "uncosted", disclosed FX. Never a number the system can't defend.
- Control, not surveillance: per-person data only in context ("contributors to this spike"), names Admin-only.

Sizes are fixed: `sm` 28px (14px icons), `default` 36px (16px icons), `lg` 40px, `icon` 36Ã—36px and `icon-sm` 28Ã—28px. ### Button motion (2026-07-18)

Button motion is centralized in `Button` and is driven by action intent, never by control size. The shared tokens are `--motion-duration-fast: 120ms`, `--motion-duration-standard: 160ms`, `--motion-duration-max: 180ms`, `--motion-ease-standard: cubic-bezier(0.22,1,0.36,1)`, `--motion-icon-shift: 3px` and `--motion-button-lift: 1px`.

**App-wide motion rule (2026-07-18 standardization):** every interaction-speed transition consumes these tokens â€” micro moves (chevrons, icon shifts, color fades on small marks) at `fast`, hover/row/content color at `standard`, overlay enter/exit (dropdown, popover, select, tooltip, dialog, sheet) at `max` â€” written as `duration-(--motion-duration-*)` + `ease-(--motion-ease-standard)` utilities (or the CSS vars directly). No raw `duration-150/200/300` and no `transition-all` in first-party code. Signature motion is the deliberate exception and uses `--motion-ease-expressive: cubic-bezier(0.16,1,0.3,1)`: the 320ms sidebar collapse, the chart reveal builds (560â€“1400ms), the 2200ms verdict pulse and the auth entrance. Focus rings are uniformly `focus-visible:ring-2 ring-ring/40`.

| Intent | Hover | Active | Focus |
|---|---|---|---|
| `primary` | Background gains contrast and the container rises at most 1px | Returns through the origin and presses down at most 1px | Stable accent ring; no movement |
| `secondary` / `outline` | Neutral surface, border and ink gain restrained contrast | Surface darkens slightly; container stays fixed | Stable accent ring; no movement |
| `tertiary` / contextual | 120ms neutral surface/border transition; only a semantic end chevron may gain accent-light and move | Directional icon falls back to a 1px displacement; container stays fixed | Stable accent ring; no movement |
| `destructive` | Controlled red surface/border contrast only | Surface pressure only; no shake, pulse or glow | Stable destructive ring; no movement |
| icon-only | Surface/contrast by default; movement only when the icon's meaning requires it | Semantic feedback only | Stable ring; no movement |

Directional controls opt into `motion="forward"` or `motion="backward"`, and mark only the semantic arrow with `data-icon="inline-end"` or `data-icon="inline-start"`.   1. **Veil (`FocusScrim`) + highlight (`HighlightLayer`)** â€” two deliberately separate layers. The veil is a plain page-coloured rect over the plot at 0.62 opacity that dims grid, area fill and every series **evenly**. **Base UI dropdown gotchas** (found 2026-07-09 fixing the sidebar profile menu): (1) `DropdownMenuLabel` wraps Base UI `Menu.GroupLabel`, which **throws "MenuGroupContext is missing" outside a `<Menu.Group>`** â€” for a plain identity header inside the menu, use a styled `<div>`, not `DropdownMenuLabel`. (2) Composing `DropdownMenuTrigger asChild` through another render-prop component (e.g. `SidebarMenuButton`, itself a `TooltipTrigger`) **swallows the trigger's open/close handlers and the menu never opens** â€” use a plain `DropdownMenuTrigger` (it renders its own native button) styled to match, with an `aria-label` for the collapsed rail.

**Button icon-size gotcha** (found 2026-07-09 â€” the header sidebar toggle rendered a 12px speck): the `Button` base carries `[&_svg:not([class*='size-'])]:size-3`, whose `:not([class*=â€¦])` gives it **higher specificity than any parent `[&_svg]:size-*` override** â€” such overrides silently lose. The intended escape hatch is a `size-*` class **on the svg itself** (that's what the `:not()` guard checks). Any icon inside a `Button` that should not be 12px must carry its own size class (e.g. `SidebarTrigger` now renders `<RiSidebarFoldLine className="size-5" />`).

**`asChild`-from-a-Server-Component gotcha** (found 2026-07-15 â€” the "Definir orÃ§amentos" button on `/times` rendered as an empty stub and the hydration mismatch garbled the card): an element passed as `asChild` children **from a Server Component** arrives at the client primitive as a `react.lazy` element (react#32392). Base UI's `evaluateRenderProp` merges the primitive's props with `render.props` *before* unwrapping the lazy element â€” `render.props` is `undefined` at that point â€” so any explicit `children` key on the primitive, **even `null`**, wins in `cloneElement` and wipes the render element's label out of the SSR HTML. Client-component call sites are unaffected (their elements are local, `render.props.children` survives), which is why the bug hides: identical JSX works on one screen and breaks on another. Fix pattern (applied to `Button`): when `render` is set, omit the `children` key entirely (`{...(render ? {} : { children })}`), never pass `{render ? null : children}` as a JSX child. `dropdown-menu.tsx`/`sidebar.tsx` still carry the generated null-children pattern but are only composed from client components today â€” apply the same fix there if a server component ever feeds them an `asChild` element.

**`Item` primitive gotcha** (found 2026-07-09 â€” `/configuracoes` rendered a blank card): `Item` is built on Base UI `useRender`, which only renders children it receives via `props`. The generated component destructured `children` out and never forwarded it, so a plain `<Item>â€¦</Item>` (no `asChild`) rendered an empty `<div>` â€” dropping the whole card content. `/ajustes` was unaffected only because its Items all use `asChild` (children come from the `<Link>` in `render`). Fixed by forwarding `children: childRender ? undefined : children` into the `useRender` props, mirroring `SidebarMenuButton`. Any `useRender`-based primitive here must forward children the same way.

**Button compatibility aliases:** `default` maps to `primary` and `accent` maps to `tertiary` only so older integrations do not break during the migration. New call sites must use the six semantic variants above; remove aliases after the remaining external/generated integrations no longer reference them.

**Native controls & the single Select** (2026-07-15): the app now sets CSS `color-scheme` (`light` on `:root`, `dark` on `.dark`) so UA-rendered controls (dropdown popups, scrollbars) follow the theme â€” before this, native `<select>` popups rendered as white OS menus in dark mode.
